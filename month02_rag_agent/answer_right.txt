Q1:区分“存储成本”和“推理成本”
10 万字保存在硬盘上并不昂贵，真正的问题是把它们全部放进 LLM 上下文：
    可能超过模型的上下文长度
    输入 Token Prefill 计算和 KVCache 占用增加
    API 成本和响应时间上升
    无关信息稀释真正的相关内容，降低回答准确率
RAG 是从大量廉价存储的数据中，只选择少量相关内容送进昂贵的模型上下文

Q2
整片文章只有一个向量时，多主题语义会被压缩、稀释、匹配不够精确
chunk 可以提供更细粒度的来源定位和引用

Q3:
chunk 较大：向量数量更少，索引可能i更小，检索更快
LLM 回答阶段每个结果包含更多 token,相关性较低，推理通常更慢

chunk 较小：向量数量更多，索引和存储更大，检索可能更慢
LLM 定位更精确，单块 token 少，但容易丢失完整上下文

Q4:
Document：完整原始内容及a来源等元数据
Chunk：从 Document 切出来的文本片段，不一定 是关键信息，通常u覆盖u全部
Embedding Vector: chunk 的定长z数值语义i表示，用于相似度计算。他通常不可逆，不能代替i原始文本
