Q1
10 万字，上下文n过长，如何全部存储下来需要占用大量的内存空间，而且有绝大多数信息基本都用不到。
推理成本太高，在 LLM 真正理解到你的真是意图，得到你的 input 前，需要处理大量的无用 prompt，做额外的无效推理
无效推理会占用大量的没有任何必要的时间开销，让整体的响应时间变慢
对应你的输入可能只有关键的几条 prompt 起到关键的限制作用，而无关信息不仅不会带来增益反而会影响输出结果

Q4
原始文档 Document:
主要存储原始的数据信息，是最基础的文本信息库，一般存在在固态硬盘，是 chunk 的基础

文本块 Chunk
存储原始文档的关键信息切片，更便于检索，是与 LLM 交互的主要信息块

Embedding Vector
信息检索向量，保存每个 chunk 的关键向量信息，用于匹配检索对应的 Chunk

query 和 chunk_a 只是数值不相等，但他们指向的方向都是一致的，夹角为0,所以相似度为1
如果只使用点积，那么无法归一化，比如幅值大的会带大相关性小的，无法统一衡量
余弦相似度为1只能说明他们相似度一致，不能证明完全一致
Top-K 返回的是前 K 个相似度最大的结果，只能说是最有可能相关的，不能作为答案也无法说明真的与问题a相关

向量的模长要作为分母，零向量的模长是0,不能作为分母

模型输出的通常是 numpy 数组，而索引最终要写入 JSON, Json 认识 Python 原始类型：list,dict,str,int,float,bool,None

我觉得这个相似度的评价上，语义接近占一定比重，但词语用词相同也应该占一定比重，所以只有语义接近不能达到1
只看uo最高分不够，i解析出来的一个种可能，无法很好覆盖所有内容，所以要综合选取

chunk 和 embed_documents 分别是切片 和对切片生成的向量
为了保证各个功能i之间的解耦，所以在 retriever.py 中做检索
那么一条检索记录中应该保留的内容有：
1. 原始 chunk 内容：用原始文本与问题对照，可语感直接判断方便后续验证
2. 原始 chunk 的序列号：方便后续检索定位到原始文本中
3. 向量：计算相关性得分以及原始向量方向
可以再增加一个原始i文件名，即原始文件名+ chunk序列号

metadata 的主要价值是把稳定的核心字段与可扩展的描述字段分层
我觉得 source 和 chunk_index 放进统一的 metadata 中更好，统一起来方便维护管理，分开在顶层中记录不方便增删查改，放进统一的在字典i返回时也方便
