### 并发与背压
背压不是“让所有请求无限等待”，而是系统主动限制进入昂贵资源的任务数量

当前路由是同步 def。两个请求同时进入时，是否有可能同时调用同一个 app.state.embedder？为什么？
同步路由：
def create_index(...):
    ...
FastAPI 会把每次请求提交到线程池。假设同一时刻来了两个请求：
Uvicorn Worker 进程
├── 线程 A：请求 1 → app.state.embedder
└── 线程 B：请求 2 → app.state.embedder
因为两个线程：
- 属于同一个 Worker 进程；
- 共享同一个 app 对象；
- app.state.embedder 保存的是同一个 Python 对象引用；
所以两个线程可能同时调用同一个 Embedder 实例。
Python 的 GIL 也不能保证模型安全，因为 NumPy、PyTorch等底层计算通常会释放 GIL，而且模型内部还可能使用 GPU、线程池和可变缓存。

为什么不能简单地通过增加 Uvicorn Worker 数量解决并发问题？提示：每个 Worker 的进程和模型实例是什么关系？
Uvicorn 主进程
├── Worker 进程 1
│   ├── Embedder 实例 1
│   └── 多个线程
├── Worker 进程 2
│   ├── Embedder 实例 2
│   └── 多个线程
└── Worker 进程 3
    ├── Embedder 实例 3
    └── 多个线程
一个 Unicorn Worker 是一个操作系统进程，不是一次线程任务
每个worker都会：
1.创建自己的 FastAPI 应用；2.独立执行 lifespan;3.独立调用一次 embedder_factory();4.在自己的内存中保存模型
4 个 Worker ≈ 4 份模型内存
模型是在 Worker 启动时创建，不是在响应请求时创建。盲目增加 Worker 可能直接造成 GPU 显存或内存耗尽。

如果并发执行槽位已经占满，你认为应该返回：
- 429 Too Many Requests
- 503 Service Unavailable
对当前“服务器模型资源暂时不足”的场景，哪个更合适？
429 更偏向某个客户端超过限流或配额；503 表示服务器当前资源暂时不可用。

为什么信号量的释放必须写在 finally 中？如果业务函数抛出 RuntimeError 后没有释放，会发生什么？
finally 里释放的是信号量的执行许可：
finally:
    semaphore.release()

它不会：

终止进程；
销毁模型；
停止其他任务。

如果异常后没有释放，许可就永久丢失。假设最大并发为 1：

初始可用许可：1
请求获得许可：0
业务抛出异常
没有 release：仍然为 0
后续所有请求：永远无法执行

1. 当前路由是通过同步 def, FASTAPI 会把它放进线程池执行，但多个线程可能同时访问同一个 Embedder,原因不是很清楚为什么
2. Uvicorn Worker 受到设备进程个数的限制，一个 worker 进程是代表一个线程任务，模型是在a响应线程任务时n创建的
3. 503 Service Unavailable 这个更合适
4. finally 中统一做信号 的释放和进程的终止，只抛出不释放导致模型任然在运行，占用计算i机i资源

一个总 deadline 为 10 秒的任务，前面已经消耗 8 秒，工具配置的 step timeout 为 5 秒，这次工具调用的有效 timeout 应该是多少？
read_file 超时后重试通常安全，而 append_file 超时后重试为什么危险？
如果客户端主动断开 HTTP 连接，是否应该直接断言 Agent 任务已经取消？还需要什么机制？
客户端断开可能是：

用户主动取消；
网络临时中断；
网关超时；
客户端进程崩溃；
客户端准备稍后查询后台任务。

应根据接口语义决定：

任务类型	客户端断开后的策略
与 HTTP 请求绑定的同步任务	可以发出取消信号
已返回 202 的后台任务	通常继续执行
有副作用的关键任务	不能仅因网络断开立即终止
可恢复的查询任务	可以协作式取消

即使决定取消，也必须：

检测断开
→ 设置 cancellation token
→ 向 Agent/工具传播
→ 工具在安全点检查
→ 清理资源
→ Trace 记录 cancelled

只抛出一个 HTTP 异常，并不能保证底层模型停止。

1. agent 不会依靠 max_steps 退出，max_steps 只限制循环次数，在工具被阻塞之后会一直被阻塞，工具没有返回，整个 agent loop 无法继续
2. 得到 TimeoutError 之后，http 调用方停止等待，future 被标记超时，工作线程中的工具可能任然在计算
3. 为 10s , 总 deadline 代表整个任务的绝对截至时间 10 -8 = 2s
4. read_file 只做文件的读取，不会修改，append_file 会修改，重试会带来不可逆的风险
5. 主动断开不能直接断言为收到取消指令，还应该考虑是不是网络等问题，但是可以都处理为 agent 任务取消，可以加入断开 HTTP 连接，就抛出取消任务指令
