1. LLMAgent.run() 中，为什么既有 self.memory，又要为每次请求创建新的 task_memory？
self.memory 是作为当前系统中的历史记忆做记忆保存；task_memory 作为当前任务的记忆保存，在查看历史记忆 observation 时避免受到其他任务历史记忆的干扰。
2. parse_action() 与 execute_action() 分别负责什么？为什么不应该合并？
parse_action 是从 llm 的输出结果中提取 action 指令，例如 Action: calculator(expression="1 + 2 * 4")；execute_action() 则是根据上述的解析结果选择对应的调用工具和输入参数。他俩之间不合并是方便解析和执行工具的解耦。解析只负责解析，执行只用于执行。
3. 工具返回 TOOL_ERROR 时，为什么 Executor 仍然返回 type="observation"，而不是直接结束 Agent？
返回 TOOL_ERROR 有多种可能，包括参数原因以及工具调用原因，对于这些错误将错误原因返回给 agent, 对错误原因加入到 observation 做进一步思考看 agent 是否能正确处理。只有 action 解析到未知类型才会直接 结束。
4. eval.py 只检查最终答案够不够？为什么还需要检查工具调用路径和 Trace？
不能只检查最终答案，有可能会出现那种 llm 直接输出最终答案没有调用应该使用的工具这种情况，所以需要加上检查工具调用路径和 Trace

LLM 决定“做什么”，Agent Loop 决定“下一步做什么”，ExecutionContext 决定“这一步现在是否仍被允许执行”。后者属于 Agent Runtime，而不是模型智能。
llm 是大语言模型，他是主要的h思考者和决策者，agent_loop 给 llm 提供基础外围设施给 llm 提供输入信息的封装和输出的解析并调用对应的工具执行。ExecutionContext 决定“这一步现在是否仍被允许执行”，是一个动作的行动许可，允许执行权限执行时间。

LLM 是概率式生成模型，根据当前上下文生成下一步动作建议，但它本身不执行工具，也不保证动作安全。Agent Loop 负责组装上下文、调用 LLM、解析输出、分发工具并维护循环状态。ExecutionContext 属于 Agent Runtime，保存一次任务的 deadline 和取消状态，在每次关键操作前判断动作是否仍允许执行。最终执行权属于 Runtime，而不是 LLM。

等待 future.result(...)

1. 前 4 个任务进入运行工作状态,后面两个进入内部的等待队列,第 7 个被拒绝
2. 此时工作线程仍在运行,释放后下一个任务执行,会造成不确定的中间过程和结果,调用方超时后，如果提前释放许可，会破坏 running + queued <= capacity 的容量不变量。不一定马上多出一个正在运行的线程，因为还受 max_workers 限制；但会错误接收新任务，让实际在途任务数超过容量。
3. 在 future 的完成回调中释放,在上一个任务完全完成后,工作线程结束,可以开启下一个任务,所以此时释放容量许可,完成回调不仅处理正常结束，还处理：工具正常返回；工具抛出异常；排队中的 Future 被成功取消。这些状态都意味着 Future 已进入终态，可以释放许可。
